# ウィンドウの運用と座標の変換

ウィンドウの拡縮・最小化・DPI・フォーカス・マウスの捕捉を、ゲームとUIがどの時点・どの座標で受け取るかをまとめます。部品の使い方は[UI入門](GettingStarted.md)、検証の結果は[2D／3D UIのウィンドウ統合の記録](../Development/UiWindowIntegration-2026-09-27.md)を参照してください。

## 1フレームの順序

1. OSのイベントを処理する（`IPlatform::PumpEvents`）。
2. `IPlatform::SyncWindow`で、そのフレームのウィンドウの状態（`FWindowState`）を一度だけ確定する。`Resizable`で描画先とクライアント領域の画素数が違えば、この境界で描画先の寸法を変える（描画中の命令はない）。
3. 最小化などで描けない場合（`CanRender()`が偽）、`bPauseWhenMinimized`なら更新も描画もしない。既定では更新だけを行い描画を省く。
4. 入力を一度取得し、`FTickContext::Window`へ確定した状態を入れて更新する。Hostの入力の仲介は、この寸法・DPIで配置と選択を行う。
5. 更新と入力の仲介が`FTickContext::Requests`（`FPlatformRequests`）へ書いた要求を、`IPlatform::ApplyRequests`でまとめて反映する（マウスの捕捉・カーソル・拡縮の扱い）。拡縮の扱いの変更による描画先の寸法の変更は、次のフレームの2で行う。
6. 描ける場合だけ、確定した描画先の寸法で描く。

フレームの途中でOSの通知から寸法・DPIが変わることはありません。前のフレームの描画の寸法を入力に流用しません。

## 変更の失敗

- `SyncWindow`が状態を取得できない、または描画先の寸法の変更に失敗した場合は、以前の状態を保って失敗を返し、`Application::Step`はそのフレームを失敗として返します（黙って古い寸法で続けません）。
- `ApplyRequests`の失敗も同様にフレームの失敗です。
- 状態を取得できないPlatform（代替等）は`bKnown = false`を返し、描画できるものとして扱います（0x0の最小化とは区別します）。

## 座標の空間

| 空間 | 単位 | 使う場所 |
|---|---|---|
| クライアント領域 | OSのウィンドウの物理画素 | `FWindowState::ClientWidth/Height` |
| 描画先 | 描画先の画素（入力の位置もこの画素） | `RenderWidth/Height`、`FRawInput::MouseX/Y`、描画命令 |
| 表示面 | 描画先の画素の矩形と倍率 | `FUiSurface`（画面・Viewport・2Dパネルの範囲） |
| UIの論理座標 | 表示面の画素÷倍率 | 要素の位置・寸法・スタイル |
| 2Dワールド | ゲームの世界の単位 | `FUiWorldToScreen2D`で描画先の画素へ |
| 3Dワールド | ゲームの世界の単位 | Viewの近接面〜遠方面の線分と平面の交点のUV→中間画像の画素 |

- `Fixed`：クライアント領域＝描画先（拡縮しない）。
- `Stretch`：描画先は起動時の寸法のまま、表示だけをクライアント領域へ引き伸ばします（縦横比は保たない）。DxLibがマウスの位置を描画先の画素へ変換して返すため、入力と描画は同じ描画先の画素です。
- `Resizable`：描画先をクライアント領域と同じ画素数に変えます。読込済みの画像・字体・描画先は保たれます（DxLibの画面モードの変更時の資源の再作成を止めて変更）。

## DPI

- 実行ファイルは`dxf_enable_dpi_awareness(<Target>)`でPer-Monitor V2のDPI認識をmanifestへ宣言します。宣言しない実行ファイルはOSにビットマップで拡大され、描画先の画素と物理画素が一致しません。
- `FWindowState::Dpi`はウィンドウのモニターのDPI（96が等倍）です。
- UIの倍率は表示面ごとの`FUiScaleSettings::Mode`で選びます。`Dpi`だけが`Dpi/96 × UserScale`でDPIを使います。`FixedPixel`・`ReferenceHeight`はDPIを使いません。位置・寸法は描画先の画素のままなので、DPIは倍率へ一度だけ入り、二重にかかりません。
- DPIが変わると（モニター間の移動）、次のフレームの境界で倍率と配置が変わります。OSのDPI変更の通知によるウィンドウの大きさの提案は、DxLibの既定の扱いに従います。

## フォーカスとマウスの捕捉

- 失焦の間、入力は何も押されていない状態になります。失焦は押下中のUIの操作を**取り消し**（決定しない）、通常の解放と区別します。
- 押したままフォーカスが戻った入力は、離す（スティックは中立へ戻す）まで渡しません。復帰したフレームの偽の押下・ジャンプ・決定を作りません。
- UIが押下を捕捉している間、Hostは捕捉を要求し、Native Platformは自アプリのウィンドウが前面の時だけOSの捕捉（`SetCapture`）を取得します。取得できたかは次のフレームの`bPointerCaptured`で分かります。取得後に失った場合はフォーカスの喪失と同じ取り消しです。
- 捕捉の間はウィンドウの外の位置も届き、Sliderは端へ制限されます。ウィンドウの外で離しても決定しません。
- カーソルは最前面の要素の意図（`GetCursorShape`）をHostが要求し、Native Platformが標準のカーソルへ反映します。

## 最小化と時間

最小化の間（クライアント領域0x0）は描画しません。既定では更新は続き、ゲームの時間も進みます。`bPauseWhenMinimized = true`では更新も止め、復帰時に止めていた時間を固定更新の追い付きへ変えません。Sceneの一時停止の状態は変えません。

## 確認していない環境

複数のDPIの実モニター間の移動、人による物理的なウィンドウ操作（端のドラッグ・最小化ボタン）、他のアプリによる捕捉の奪取の実操作は未確認です。自動の確認はOSのAPIでのウィンドウの寸法の変更・最小化・復帰、前面での捕捉の取得と解放、DPI認識の宣言の確認（単一の96 DPIのモニター）までです。
