# 透明3D描画パス

基準main: `86a37b9cdb7e3641e41f7838a8c5694de801679c`。
描画入口は `Render.Get2D()` / `Render.Get3D()` のみ。互換のroot Draw/DrawTextや旧Renderer型は追加しない。

## 実行順

同じSetView区間・同じFlush区間ごとに次の計画を作る。

1. Sceneの不透明プリミティブ（A=255）。既存の入力順を維持する。
2. Sceneの半透明プリミティブ（0<A<255）。奥から手前へ安定ソートする。
3. OverlayとDepth=Always。入力順で重ねる。

実効色のA=0は描かない。完全透明な形状しかないビューはBeginViewも呼ばない。
入力・形状・設定の検証を省くわけではない。A=0でも不正な形状・enumは失敗とする。

2D命令はそのFlushの3D処理後に、2D状態へ復元して実行される。
SetViewの呼出し番号を境界に使う。同じView.Idで別のカメラを設定しても混ぜない。
Native/描画先切替などが作るFlush境界を越えて並べ替えない。

## ソートの意味

三角形は三頂点の重心、線は二端点の中点を、EyeからTargetへ向かう単位方向へ射影する。
距離二乗ではなく符号付きのカメラ前方向の距離を使う。
入力f32をf64へ移してから差・重心・射影を計算し、中間オーバーフローや早すぎる丸めを避ける。
ただし入力の時点でf32から失われた精度を復元するものではない。

ソートは命令全体の中心ではなくプリミティブ単位。別命令に含まれる三角形同士も並び替わる。
線と面を同じ索引列で並べ、同種が連続する部分だけNativeパケットへまとめる。
キーが等しい場合は受付順。通常の並列生成も結果を添字順に統合するためレーン数に依存しない。
一つのFGeometry3Dの中では従来同様にTriangles配列→Lines配列が元の入力順である。

## 深度と重ね表示

- 不透明Scene：指定されたDepthを維持する。
- 半透明Scene：深度検査あり、深度書き込みなし（TestOnly）へ変換する。
- Overlay：深度を書かない。TestAndWriteを指定されてもTestOnlyにする。
- Depth=Always：Layer指定にかかわらずOverlay。深度検査も書き込みもしない。

`FDrawStyle3D::Layer`の既定値は`ERenderLayer3D::Scene`。
補助線をSceneの後に載せたい場合は`ERenderLayer3D::Overlay`を指定する。
これは独立の描画APIではなく、同じGet3D入口へ渡す設定である。

```cpp
Dxf::FDrawStyle3D Style;
Style.Color = {70, 120, 255, 128};
auto Result = Render.Get3D().DrawBox(Box, Style);
if (!Result)
{
	throw Toolbox::FException(Result.Error().Message);
}
```

DebugDrawStore3Dの描画アダプター、PhysicsDebugDisplay3D、デバッグ用グリッドはOverlayへ分類する。
SolidWithEdgesで自動生成する辺もOverlayにする。A=0の元図形から不透明な辺だけを作らない。
これらは半透明物体の後に重なるが、TestOnlyなら不透明物体に対する遮蔽は維持する。
重ね表示は透明面より奥にあっても透明面に遮られない場合があり、これは調査用Overlayの契約である。

## 失敗と寿命

PrepareGeometry3Dと全ビューのパス計画・索引・配列確保を、最初のNative状態変更より前に済ませる。
途中確保失敗時にはNative Begin/Draw/Presentを実行しない。受理済み命令の入力値は呼出しの所有規則に従う。
描画を開始した後のBackend失敗では既存のエラー規則を維持し、EndViewと2D状態復元を試み、最初の失敗を保持する。
部分的に描いた画素はロールバックできない。失敗フレームは成功としてPresentしない。

描画キューは同じ所有スレッドで使い、Workerや生成コールバックから自由に操作してよいAPIではない。
元の形状と色・ビュー設定を描画上書きのために書き換えない。
Native自身の任意の外部状態を全部保存・復元する保証は追加していない。

## サンプル

前回のRenderDebugを引き継ぎ、F7で三枚のRGB半透明パネルをON/OFFする。
カメラを動かした際の順序はRendererが決める。サンプル側で前後を決め打ちしない。
F1の塗り/ワイヤー/辺付き、F2の照明切替、既存の物理停止・カメラ・履歴と組み合わせられる。
確認時はまずF2でUnlitにすると、照明の明るさと合成順を切り分けやすい。

TransparencyDemo.cppの命令生成とRendererへの投入経路はテストで実行した。
RenderDebugScene全体とWindowsの実画面はこの環境では未ビルド・未実行。

## 対応限界

- 基本形状/CPUの色付き三角形・線のみ。MV1、スキニング、テクスチャ付きモデルは未対応。
- 透明面の重心順は近似。交差/循環する面、大きな傾斜面、自己交差、カメラを跨ぐ面の画素単位順を保証しない。
- OIT、面分割による厳密順序、アルファテスト、加算/屈折等のMaterialパスは実装していない。
- 透明物体は深度を書かないため、それを遮蔽物として使うデバッグ線の遮蔽はしない。
- Viewport/複数window、任意ライト/影、GPU計測の対応を広げた変更ではない。
- パケット数・CPUの変換/ソート/配列の費用は増える。実ゲームの性能改善率は未測定。
