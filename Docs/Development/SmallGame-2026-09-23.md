# 小さいゲームからの利用経路確認（2026-09-23）

## 目的と変更

作業開始時のmainは`2723d17136d4ab7ec94158238d3ca6e986ebf50b`、origin/mainと一致し、作業ツリーはクリーンでした。

主目的を「DxLibを使いやすくし、ゲーム固有の処理へ集中できるフレームワーク」としてREADMEに明記しました。内部の責務分離、利用側の単純な公開API、必要な層だけの利用を機能追加の判断基準とします。モデルやViewerはその中の一領域です。

今回、Sandboxの既存DPlayer／SpriteComponent／入力／音声処理を再利用し、タイトル→右端への移動→結果→リトライを構成しました。タイトル・結果はオブジェクト集合を必要としないDScene、プレイはDGameSceneです。従来の機能サンプルへもタイトルのSpaceから入れます。Starterは空の開始点を保っています。

## 利用側から見つかった点

- 起動側でProjectRootを設定しているのに、Sandboxへ絶対パスを再構築して渡していました。通常経路は既定の`Assets`相対パスへ整理しました。既存のカスタムAssetRoot指定は残しています。
- Scene切替・旧オブジェクトの破棄・音声スコープの終了・資源解放は既存のApplicationの責務でした。例に手動Deleteやキャッシュ掃除を追加する必要はありませんでした。
- 読み込み失敗では元のSceneが保持され、GetLastTransitionErrorで理由を取得できます。タイトルに理由と再試行操作を表示しました。Scene要求の受付成功と、次の境界での初期化成功は区別しています。
- 結果の秒数は既存のScene時計から取得できます。ポーズ用時計や別のタイマー管理を追加していません。
- タイトル・結果はゲーム用オブジェクトや独自GameInstanceを必要としません。共通の大きい基底SceneやSubsystemを先に作らず、ゲーム固有の値と操作だけを追加しました。

今回はフレームワーク本体の公開APIを増やす必要はありませんでした。新しい用途でも同じ初期化・失敗処理が反復される場合には、その実例を根拠にAPIの簡略化を検討します。今回だけでフレームワーク全体の使いやすさを証明したとはしません。

ログは`Build/FbxContinuation/game-*-build.log`、`game-*-tests.log`、`game-python-tests.log`、`game-package.log`へ保存しました。画像は`sandbox-smoke-Debug`と`sandbox-smoke-Release`のtitle/play/result/retry.pngです。ログ・画像・SDK・ビルド生成物はコミット対象外です。

NativeSandboxSmokeは開発用のDXF_BUILD_NATIVE_SMOKEにのみ属し、通常の生成ではOFFです。通常のソリューションにテスト用プロジェクトを増やしていません。実行画像の出力先が既存でも再実行できるようにしています。

## 限界と次の判断材料

OSの物理キー入力を操作する試験、音声の聴感確認、ユーザー自身による制作時間の評価は未実施です。Starterへサンプルをコピーする手順は案内しましたが、そのコピー先を別途生成・実行した試験ではありません。Starter本体の空起動試験とSandbox本体の実描画試験を区別しています。

基本的な利用手順は[小さいゲームを組む](../SmallGame.md)へまとめました。次の改善も、実際のゲーム側で繰り返す準備・内部依存・手動管理を観察して選びます。GPUモーフや追加の描画機能へ今回の作業範囲を広げていません。
